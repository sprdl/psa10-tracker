# Quick price check (SNKRDUNK tiles and sales)

The quick-check procedure of the `pokemon-card-price-check` skill. `pricecheck/start.py --mode quick`
(or a mode check that chose quick) prints this file followed by the browser call for today's cards.

Refreshes, for every card on the tracker: the lowest PSA10 and raw-A ask (SNKRDUNK's grade tiles), recent one-copy completed sales (売買履歴) for both grades, and favorites. Depth, population and the index are carried from the last full check and labeled "as of" on the site, except for cards in Focus watch (`data/focus.json`): the browser call lists them as `<id>:L` and also reads their PSA10 listings, so their book depth is fresh on every check (about 10 s per focus card; their line ends with an `L=…` token, pass it along like the rest). A quick check also adds requested cards (Q0) and evaluates new ones (Q5), so a request never forces a second full check. It never does the My-tier index, the release calendar, tier reviews or stories (the next full check does a new card's story, depth, population and photo). It does the other small follow-up when it's due (Q5): the SNKRDUNK name and picture of newly logged sealed products.

The script opens the cards' own product pages in hidden same-origin iframes of the tab, one after another (the same pages a person would open). It makes no fetch/XHR requests. Never use curl, requests, or any HTTP client.

**Q0. Add requested cards** (only when the setup listed open requests). Get a tab id first (Q2), then follow `pricecheck/steps/1b-add-cards.md` for each request (`cat "$R/pricecheck/steps/1b-add-cards.md"`). In short: open the card's SNKRDUNK page, run `pricecheck/scripts/snkrdunk_base.js` and `grade_tiles.js` there, read the photo URL, then `python3 scripts/card_requests.py add <issue#> --name "<title>" --image "<photo>"` (or `reject` with the reason). Then re-print the browser call with `python3 pricecheck/jsrun.py quick`: its IDS now include the new card.

**Q1. The browser call.** The setup output below this file holds the `snkrdunk_quick` block: a RUN call with today's card ids filled in (`jsrun.py`'s `quick_ids()`: every card in the latest snapshot plus just-added ones, minus removed cards) and a POLL call. If it's missing (for example after a context compaction), one `device_bash` call: `cd "$R" && python3 pricecheck/jsrun.py quick`.

**Q2. Run it, once, for all cards.** Get a tab id (`tabs_context_mcp` with createIfEmpty, or a standalone `navigate`) and `navigate` it to `https://snkrdunk.com/apparels/<first id>`. Then one `javascript_tool` call with the RUN call, verbatim. It returns `started N cards` at once and keeps working in the page (about 3 s per card). The RUN call runs the cached copy of the script only if its SHA-256 matches the repo version and the filled-in card list matches what `jsrun.py` built; otherwise nothing runs and it answers:
- `NEED_SCRIPT snkrdunk_quick (…)`: one `device_bash` call, `cd "$R" && python3 pricecheck/jsrun.py store snkrdunk_quick`; paste the STORE call it prints on the same tab (`stored …`), then the RUN call again. `STORE REFUSED`: paste the STORE call again, verbatim.
- `EVAL_BLOCKED` / `STORE FAILED`: paste `python3 pricecheck/jsrun.py inline snkrdunk_quick` instead (the filled-in script itself, the old way) and mention it in the chat message.
- `RUNNER ERROR`: re-print the call with `python3 pricecheck/jsrun.py quick`; never edit a call by hand.

**Q3. Collect the lines.** Call `javascript_tool` with the POLL call until it returns lines instead of `running i/N` (each call waits up to ~37 s). One line per card: `<id> f<favorites> p<PSA10 tile> a<A tile> P<PSA10 sales> A<A sales>`, or `<id> E<reason>` if the card's page failed. The script's header comment documents every code. Don't interpret or reformat the lines. If two polls in a row show no progress, stop and report it rather than polling on.

**Q4. Publish, in one `device_bash` call.** Paste the lines verbatim into a heredoc and hand them to `quick_update.py`:
```
R=$(ls -d "$HOME"/mnt/*/psa10-tracker "$HOME"/mnt/psa10-tracker 2>/dev/null | head -1); cd "$R" && python3 scripts/quick_update.py - <<'EOF' 2>&1 | tee data/incoming/quick-update.log | tail -50
<the lines>
EOF
```
`quick_update.py` decodes the lines into the same raw JSON the old quick check produced (and keeps them in `data/incoming/quick-raw.txt`), pulls, builds the new snapshot from the latest one (a card added in Q0 is published for the first time, from its `tracked_cards.json` entry: "NEW card(s) published"), then hands off to `add_snapshot.py`, which carries the analysis, commits and pushes. Its "tracked-card set differs" warning is expected when Q0 added a card. The repo has its own credential file configured. **Never put a token or credential in any command**, and never ask the user for one. If a push fails with an auth error, tell the user the token in `.psa10-git-credentials` may have expired. If `git pull --ff-only` or the push fails because the history diverged, don't force anything; tell the user to run `git pull` then `git push` in the repo on their Mac. If git fails with `unable to unlink ... .git/index.lock: Operation not permitted`, call `device_request_delete_permission` for that folder once, then `rm -f .git/index.lock` and re-run. The push succeeded if the output says "Pushed." The whole output is kept in `data/incoming/quick-update.log` in case the shown part was cut.

If a card came back as an `E` line, `quick_update.py` keeps that card's values from the last snapshot and lists it under "NOT re-checked"; you may retry just those ids once: `python3 pricecheck/jsrun.py quick --ids <id>,<id>` prints a RUN call for only them (run it on the same tab after the first run is done, then POLL), then publish all lines together, the retry's lines after the first run's (`quick_update.py` keeps the last line it sees for a card, so a successful retry replaces its `E` line). If the whole run fails (e.g. the script reports the page structure changed), fall back to reading one card by hand with `pricecheck/scripts/snkrdunk_base.js` + `pricecheck/scripts/grade_tiles.js` on its product page, and flag it at the end so the script can be fixed.

**Q5. Follow-ups (required when listed).** The last line of `quick_update.py`'s output is `FOLLOW-UPS (required before the chat message): …`, or `none`. Do each step it lists before writing the chat message; the blocks just above it (`EVALUATE NOW`, `SEALED INFO NOW`) hold the details:
- **Evaluate** (`EVALUATE NOW`), first: new or restored cards, and cards whose PSA10 market just formed. Follow the skill's "New cards" step 3 (`eval_context.py`, then the `pokemon-tcg-card-evaluation` skill, applied with `apply_analysis.py`; the full rules are in `pricecheck/steps/8b-evaluate.md`). For a card Q0 just added, the quick run only read its tiles and sales, so the evaluation reads its listing depth and finds its PSA pop page itself (`pricecheck/steps/1c-psa-pop-pages.md`; a brand-new print PSA doesn't list yet stays without population); save it with `card_requests.py set <id> psa_pop_url=<set page path> psa_pop_no=<number> psa_pop_name="<English name>"`, and apply a first reading right away with `python3 scripts/psa_pop.py apply -` (the `psa_pop.js` POP line for that card).
- **Sealed info** (`SEALED INFO NOW`: sealed products logged with a SNKRDUNK link but no name or picture yet): follow `pricecheck/steps/8h-sealed.md` (the `snkrdunk_sealed` RUN call on a snkrdunk.com tab, poll, then save the `SP`/`SE` lines with `python3 scripts/sealed_info.py -`).
- Any other block a future version prints names the document to follow; do the same.
If a step fails (site down, page changed), say so in the chat message instead of retrying repeatedly.

**End of the run.** After the last follow-up, one `device_bash` call: `cd "$R" && python3 scripts/runclock.py end`; it prints how long the run took. It also pushes the follow-ups (analyses, insights, stories, hype readings): during a run those scripts only commit, so the site redeploys once instead of after each one (`scripts/deferpush.py`). Never skip this step; if its line says commits were NOT pushed, tell me.

**Chat message (quick check):** one or two lines, plus one line per follow-up. If `quick_update.py` printed a `FOCUS WATCH` block, add one line per focus card right after the first line: status, lowest ask and its move, the gap to the target, the sales since the last check with prices, the BOOK DEPTH line (count within 3%, its change and the last reads), and every flag marked `!` (scripts/focus.py). Card requests and evaluations as in the skill's "New cards" step 4: every card in `EVALUATE NOW` appears as evaluated or as "NOT evaluated: <name> — <concrete reason>"; being new is never the reason. Say it was published (snapshot time), or why not. Mention any card it couldn't re-check or any tile/sales problem `quick_update.py` printed. Sealed info: "Sealed: added name and picture for <product>". The site's banners already flag cards that crossed a tier line. Finally, report how long the price check took (the `runclock.py end` line) and how many tokens you used.
